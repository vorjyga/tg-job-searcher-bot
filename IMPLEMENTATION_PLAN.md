# План реализации Telegram-бота для поиска сообщений

## 1. Цель и границы первой версии

Личный Telegram-бот отслеживает сообщения в выбранных чужих группах, ищет заданные для каждой группы ключевые слова и отправляет владельцу уведомления в личный чат.

Добавить бота в группы нельзя, поэтому чтение выполняется через Telegram-аккаунт владельца с помощью Telethon. Обычный бот используется для команд, диалогов настройки и уведомлений. Подключённый аккаунт должен состоять в отслеживаемых группах и иметь доступ к их сообщениям. ID или ссылка сами по себе не дают доступа.

Первая версия рассчитана на одного владельца и один подключённый Telegram-аккаунт. Настройки, задания и результаты хранятся в **PostgreSQL, уже установленной на сервере**. SQLite для прикладных данных не используется.

## 2. Технологии

- Python 3.12: приложение и фоновые задачи на asyncio.
- aiogram 3: команды, кнопки, пошаговые диалоги и отправка уведомлений через Bot API.
- Telethon: авторизованный пользовательский клиент для чтения новых сообщений и истории.
- PostgreSQL: настройки, состояние диалогов, задания, контрольные точки и очередь уведомлений.
- SQLAlchemy 2 + asyncpg: асинхронная работа с базой.
- Alembic: миграции схемы базы.
- pytest: проверки логики поиска и сценариев; интеграционные проверки на отдельной PostgreSQL-базе.
- systemd: запуск и автоматический перезапуск приложения на сервере.

Версии зависимостей фиксируются при реализации после проверки совместимости. Redis и отдельный брокер задач для первой версии не нужны: задания и очередь сохраняются в PostgreSQL.

## 3. Пользовательские сценарии

### Добавление группы

1. Пользователь отправляет `/add`.
2. Бот просит ссылку, `@username` или числовой ID группы.
3. Telethon разрешает ссылку/ID и проверяет, что аккаунт уже состоит в группе и может читать её сообщения.
   - При недоступной или нераспознанной группе бот объясняет причину и предлагает выбрать группу из доступных диалогов аккаунта.
   - Приватная пригласительная ссылка не используется для автоматического вступления: при необходимости пользователь вступает самостоятельно и повторяет добавление.
   - Если группа уже настроена, бот открывает её карточку.
4. Бот спрашивает: «Какие ключевые слова использовать для этой группы? Введите через запятую».
5. Пользователь вводит слова и фразы, например `python, backend developer, #вакансия`.
6. Бот убирает пустые значения и дубликаты, показывает список и предлагает режим:
   - **Найти за последние 7 дней и следить**.
   - **Только следить за новыми**.
7. После выбора бот сохраняет настройку и подтверждает включение мониторинга.
8. При выборе истории создаётся фоновое задание. Бот сообщает о старте и завершении: сколько сообщений проверено и сколько совпадений найдено.

До завершения шага 6 группа не включается в мониторинг. `/cancel` отменяет текущий диалог без частично применённых настроек. Незавершённый диалог сохраняется в PostgreSQL и может быть продолжен после перезапуска.

### Управление группами и словами

- `/start` — описание возможностей и кнопка перехода к группам.
- `/help` — команды и правила поиска.
- `/add` — добавление группы.
- `/groups` — список отслеживаемых групп с переходом в карточку.
- `/cancel` — выход из текущего диалога.
- `/status` — состояние подключения, активные сканирования и очередь уведомлений.

Карточка группы показывает название, ключевые слова, состояние доступа и кнопки:

- **Добавить ключи** — ввод дополнительных слов и фраз.
- **Удалить ключи** — выбор существующих ключей для удаления.
- **Заменить все ключи** — ввод нового полного списка.
- **Просканировать 7 дней** — отдельный повторный поиск по текущим ключам.
- **Удалить группу** — подтверждение с названием группы, затем отключение мониторинга и отмена её незавершённых заданий и уведомлений.

Удаление группы из бота не выводит Telegram-аккаунт из самой группы. Если удалены все ключи, мониторинг группы приостанавливается до добавления хотя бы одного ключа. Бот явно сообщает об этом.

При изменении ключей новые настройки применяются к последующим сообщениям. История автоматически не пересканируется. Уже запущенный исторический поиск использует сохранённый снимок ключей; это указывается в сообщении о задании. Удаление группы отменяет такой поиск.

### Уведомления

Одно найденное сообщение — одно уведомление со следующими полями:

- название группы;
- дата исходного сообщения;
- все совпавшие ключи;
- текст или подпись к медиа;
- ссылка на исходное сообщение, если её можно сформировать;
- отметка «Из истории», если результат найден при сканировании.

Медиа, OCR и распознавание аудио в первую версию не входят. Длинный текст сокращается до лимита Bot API с сохранением ссылки. Для сообщений без доступной ссылки выводятся название группы и ID сообщения. Текст экранируется перед отправкой с HTML-разметкой.

## 4. Правила поиска

- Ключи индивидуальны для каждой группы.
- Достаточно совпадения любого одного ключа: логика OR.
- Поиск без учёта регистра, с Unicode-нормализацией и нормализацией пробелов.
- Одиночные слова ищутся с учётом границ слов: `java` не совпадает с `javascript`.
- Фразы ищутся как последовательность слов с нормализованными пробелами.
- Хештеги и технические ключи вроде `#вакансия`, `C++`, `C#`, `.NET`, `node.js` обрабатываются отдельно от обычных слов; поведение закрепляется примерами в тестах.
- Нет морфологии, перевода, регулярных выражений от пользователя или семантического поиска.
- Проверяются текст сообщения и подпись к медиа. Служебные сообщения пропускаются.
- Редактирование сообщения в первой версии не создаёт новое уведомление; отслеживаются новые сообщения и доступная история.
- Несколько совпавших ключей в одном сообщении объединяются в одно уведомление.

## 5. Архитектура

Один процесс приложения запускает несколько асинхронных компонентов:

1. **Bot UI** — aiogram с long polling; доступ только разрешённому Telegram user ID.
2. **Telegram reader** — Telethon, обработчик новых сообщений и чтение истории.
3. **Matcher** — независимая функция поиска ключей в тексте.
4. **Monitoring service** — управление группами, ключами и контрольными точками.
5. **Scan worker** — выполнение сохранённых заданий исторического поиска с ограниченной параллельностью.
6. **Notification worker** — отправка результатов из PostgreSQL-очереди с повторами и ограничением скорости.
7. **Recovery worker** — восстановление незавершённых заданий и пропущенных сообщений после перезапуска.

Бот и чтение новых сообщений продолжают работать во время сканирования истории. Для первой версии допускается только один активный экземпляр приложения; PostgreSQL advisory lock защищает от случайного запуска второго.

## 6. Модель данных PostgreSQL

Все даты хранятся как `timestamptz` в UTC. Telegram ID хранятся в `bigint`.

| Таблица | Основные поля и назначение |
| --- | --- |
| `owners` | Разрешённый `telegram_user_id`, личный `notification_chat_id` |
| `tracked_groups` | Владелец, Telegram chat ID, название, username, статус, `monitoring_started_at`, контрольная точка обработки, версия настроек |
| `keywords` | Группа, исходное и нормализованное значение ключа |
| `conversation_states` | Пользователь, шаг диалога, черновик данных в JSONB, срок действия |
| `scan_jobs` | Группа, тип задания, начало/конец диапазона, снимок ключей, курсор, статус, счётчики, попытки, время следующего повтора, ошибка |
| `message_matches` | Группа, ID исходного сообщения, найденные ключи, дата сообщения, источник `live/history/recovery` |
| `notification_outbox` | Ссылка на совпадение, подготовленный текст, статус, попытки, время следующего повтора, ID отправленного уведомления |

Ограничения и индексы:

- Уникальная группа по `(owner_id, telegram_chat_id)`.
- Уникальный нормализованный ключ внутри группы.
- Уникальное совпадение по `(group_id, telegram_message_id)` и одно уведомление на совпадение.
- Индексы на статус и время следующей попытки для заданий и очереди.
- Создание совпадения и уведомления выполняется в одной транзакции.
- Повторное сканирование не рассылает уже найденные сообщения заново, даже если изменились ключи.

При удалении группы сохраняется минимальный журнал идентификаторов ранее найденных сообщений для защиты от повторов при повторном добавлении. Полный текст сообщения нужен только для доставки и удаляется из очереди после успешной отправки. Срок очистки завершённых заданий и журнала настраивается отдельно; очистка журнала ограничивает срок защиты от повторов.

## 7. История, новые сообщения и восстановление

### Первоначальное включение

1. Обработчик событий Telethon регистрируется при старте приложения, до разрешения команд добавления групп.
2. При активации группы сохраняется время `T0` и контрольный ID последнего сообщения.
3. Режим истории создаёт задание на диапазон `[T0 − 7 дней, T0]`.
4. Новые сообщения обрабатываются после границы активации. Короткая проверка перекрывающего диапазона закрывает возможную гонку между регистрацией группы и поступлением событий.
5. Оба пути используют общую транзакционную защиту от дубликатов.

### Сканирование

- Читать историю страницами, останавливаться на нижней временной границе.
- Сохранять курсор после каждой успешно обработанной страницы.
- Не предполагать, что аккаунту доступна полная история: сообщать об ограниченном доступе и частичном результате.
- Учитывать `FloodWait`: сохранять время продолжения и возобновлять задание позднее, не блокируя интерфейс бота.
- Повторный запуск того же активного сканирования открывает его статус, а не создаёт дубликат задания.

### Перезапуск и потеря связи

- Восстановить активные настройки, диалоги, задания и очередь из PostgreSQL.
- Дочитать сообщения после последней подтверждённой контрольной точки, чтобы покрыть период простоя.
- Контрольная точка означает непрерывно обработанный диапазон; нельзя просто повышать её до максимального ID при событиях, пришедших не по порядку.
- При потере доступа к группе приостановить её обработку и один раз уведомить владельца; дать возможность повторить проверку.
- Обрабатывать временные сетевые ошибки с ограниченными повторами и увеличением задержки.

PostgreSQL предотвращает повторное создание уведомления при одновременной обработке истории и новых сообщений. Однако Bot API не обеспечивает идемпотентную отправку: при сбое после доставки, но до фиксации результата в базе редкий повтор возможен. Не обещать строгую доставку «ровно один раз».

## 8. Конфигурация и авторизация

Переменные окружения:

```dotenv
BOT_TOKEN=
OWNER_TELEGRAM_ID=
TELEGRAM_API_ID=
TELEGRAM_API_HASH=
TELEGRAM_SESSION_PATH=
DATABASE_URL=postgresql+asyncpg://USER:PASSWORD@HOST:5432/DB_NAME
LOG_LEVEL=INFO
```

- Бот создаётся через BotFather; владелец сначала открывает с ним личный чат и отправляет `/start`.
- Для Telethon нужны API ID/API hash и однократная интерактивная авторизация с кодом и, если включён, паролем 2FA.
- Авторизация выполняется отдельной CLI-командой на доверенной машине, не через диалог с ботом.
- Чтобы не создавать SQLite-файл сессии Telethon, использовать `StringSession`, сохранённую отдельным секретным файлом по `TELEGRAM_SESSION_PATH` с правами `0600`.
- Секреты, сессия и содержимое личных сообщений не попадают в Git или обычные логи.
- Все команды и callback-кнопки проверяют ID владельца; изменение чужих объектов по подставленному ID запрещено.
- В существующей PostgreSQL создать отдельную базу и пользователя приложения с необходимыми правами. Настройки других приложений не менять.

## 10. Этапы реализации

### Этап 1. Основа и база

- Создать Python-проект, конфигурацию, пример окружения и исключения Git.
- Добавить подключение к PostgreSQL, модели и миграции Alembic.
- Настроить структурированные логи без секретов и корректное завершение процесса.
- Реализовать защиту от второго активного экземпляра.

**Результат:** приложение запускается, проверяет конфигурацию и соединение с базой; миграции применяются на пустой тестовой базе.

### Этап 2. Telegram-подключения

- Создать CLI авторизации Telethon с секретным файлом StringSession.
- Подключить aiogram, `/start`, `/help` и проверку владельца.
- Реализовать получение доступных групп и разрешение ссылки/ID.

**Результат:** владелец общается с ботом, приложение читает доступную аккаунту тестовую группу.

### Этап 3. Диалоги и управление

- Реализовать весь `/add`, выбор режима и `/cancel`.
- Сохранять состояния диалога и применять настройки атомарно.
- Добавить `/groups`, карточки, добавление/замену/удаление ключей и удаление группы.
- Обработать устаревшие кнопки и повторные нажатия.

**Результат:** все настройки управляются через Telegram и сохраняются после перезапуска.

### Этап 4. Новые сообщения

- Реализовать matcher и обработку текста/подписей.
- Добавить PostgreSQL outbox, отправку уведомлений и защиту от повторной обработки.
- Реализовать границу включения мониторинга и применение обновлённых ключей.

**Результат:** новые подходящие сообщения приходят владельцу с найденными ключами и ссылкой.

### Этап 5. История и восстановление

- Добавить задания сканирования последних 7 дней и кнопку повторного запуска.
- Реализовать курсоры, снимки ключей и отчёт о завершении.
- Обеспечить параллельную обработку новых сообщений без повторов на пересечении диапазонов.
- Добавить восстановление после простоя, `FloodWait`, обработку потери доступа и `/status`.

**Результат:** история сканируется в фоне; после перезапуска задания и доставка продолжаются.

### Этап 6. Проверка и размещение

- Выполнить проверки ниже на отдельной базе и тестовой группе.
- Подготовить README: установка, PostgreSQL, миграции, авторизация, запуск, обновление и диагностика.
- Добавить systemd unit с автоматическим перезапуском и закрытым файлом окружения.
- На сервере использовать существующую PostgreSQL; проверить резервное копирование базы и сохранность файла сессии.
- Провести сквозную проверку после запуска сервиса.

**Результат:** сервис работает независимо от компьютера владельца и автоматически запускается после перезагрузки сервера.

## 11. Критерии приёмки и проверки

- `/add` проходит все шаги в требуемом порядке и предлагает оба режима.
- «Только новые» не рассылает сообщения до активации группы.
- Поиск за 7 дней соблюдает временную границу и работает одновременно с мониторингом новых сообщений.
- Ключи одной группы не влияют на другую; добавление, замена и удаление применяются корректно.
- Покрыты регистр, кириллица, фразы, границы слов, хештеги, `C++`, `C#`, `.NET`, пустой ввод и дубликаты.
- Несколько ключей одного сообщения дают одно уведомление.
- Повторные события, повторный поиск и пересечение истории с live-обработкой не создают повторные строки очереди.
- Сбой посреди страницы истории или обработки сообщения не приводит к пропуску диапазона после восстановления.
- Удаление группы отменяет ожидающие задания и уведомления; уже начатую сетевую отправку отменить гарантированно нельзя.
- Недоступная группа, потеря авторизации и ограничения Telegram отображаются понятным сообщением.
- Посторонний пользователь не может управлять ботом через команды или callback-кнопки.
- Миграции и конкурентная обработка проверены на PostgreSQL, а не на подмене SQLite.
- Сквозной сценарий: добавить группу → задать ключи → просканировать историю → получить новый пост → изменить ключи → удалить группу.

## 12. Что потребуется перед запуском

- Токен бота, Telegram user ID владельца, API ID и API hash.
- Авторизация аккаунта, уже состоящего в нужных группах.
- Доступ к серверу и параметры подключения к существующей PostgreSQL.
- Выделенные база и пользователь приложения.
- Одна тестовая группа для проверки уведомлений и восстановления.
